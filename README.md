# 指标日志链路融合｜AIOps 二期实战，掌握故障根因定位核心能力

云原生架构普及之后，业务拆分为数十上百个微服务，一次用户请求会横穿多个服务、数据库、消息队列。传统运维依靠单一指标告警，经常出现告警风暴，同一个故障触发十几条告警，运维很难分辨源头，根因定位成为稳定性工作最大瓶颈。AIOps 二期实战聚焦指标、日志、链路三类观测数据融合，训练故障根因定位能力，建立可落地的智能化排障体系。

时序指标擅长量化描述系统状态，响应延迟、错误码占比、资源负载等数据，可以快速识别异常波动，是故障发现的第一道入口。但指标是高度聚合的数据，只知道接口报错上升，无法知道是参数错误、SQL 慢查询还是下游服务超时。原始日志记录服务内部执行细节，异常堆栈、业务参数、第三方返回信息，提供丰富的上下文，缺点是数据量大、碎片化，缺少服务之间的关联关系。分布式链路追踪恰好补齐短板，还原请求流转路径，标注每一段调用耗时与状态，看清故障沿着服务拓扑如何扩散。

实战核心思路是建立统一关联模型，以请求 ID、实例 ID、服务名称、时间戳作为关联主键，把三类数据绑定到同一个服务拓扑之上。当异常指标触发告警，平台自动检索同时间段、同实例下的错误日志，并且回溯相关调用链路，标记链路中的慢节点与失败节点。依托拓扑图进行概率推理，对比正常基线，排除表象告警，输出排序后的可疑根因清单，附带证据信息。

实战过程需要攻克大量工程难点：不同组件数据采集口径不一致、日志格式杂乱、链路采样率平衡、长尾链路丢失等问题。同时区分不同故障场景，比如资源瓶颈、代码异常、依赖故障、配置错误，训练模型区分不同故障特征，不断优化根因排序准确率。

这套能力落地之后，改变以往 “先看指标、再搜日志、手动查链路” 的串行排查方式，变成多源数据联动并行分析。运维人员不用在多个监控平台来回切换，直接查看根因结论与证据。AIOps 二期是智能化运维的关键一步，核心不是替代运维，而是放大运维人员的判断效率，在复杂分布式环境下，稳定、高效定位故障根源，守住业务稳定性底线。
